# 本地大模型实战第 1 周：从第一次调用，到让 AI 查资料、用工具

**AI芯世界 · 大模型学习实战**

在工厂问答系统里，“设备报警怎么复位？”和“昨天有多少次停机？”看起来都是提问，背后的动作却不同。前者要查操作手册，后者要查业务记录。这一周，我们用本地运行的 `qwen3:8b` 做四个小实验，看看一个问题怎样变成可校验、可执行的程序输入。

## Day 1｜先观察模型究竟收到了什么

模型接口里，`messages` 是按顺序排列的消息。上下文是当前请求提供给模型的信息。Token 是模型处理文本的单位，数量与字数并不一一对应。

第一个实验请模型记住练习编号 `AI-07`。第二轮把上一轮的用户问题和助手回复一并发回，再问“刚才的练习编号是什么？”。在本次实测中，流式输出返回了 `AI-07`。

试着去掉上一轮消息再问一次。这个对照能帮你区分两件事：应用保存了什么，以及本次请求实际给模型看到了什么。随着历史增长，可以尝试只保留与当前问题相关的消息，再观察回答是否丢失关键信息。

## Day 3｜把提示词写成可验收的任务

可以借用 CRISPE 的组织思路，把角色、背景、任务和输出要求写清楚，再通过案例迭代。对路由任务来说，最有价值的一步是把“理解这个问题”改成“在四个标签中选择一个”。

| 提问 | 预期路由 | 下一步 |
|---|---|---|
| 怎样复位设备报警？ | `knowledge` | 检索操作手册 |
| 昨天一线产量是多少？ | `data` | 进入受控查询流程 |
| 先解释良率口径，再查询昨天良率 | `mixed` | 先核对口径，再查询 |
| 帮我查一下那个 | `clarify` | 询问缺失的对象 |

让模型返回 `{"route":"knowledge"}`，随后用 Pydantic 校验。这里有两种不同的失败。格式错误会被解析器拦下，标签合法但分类错误需要用有预期答案的题集发现。上线时还需根据用户身份校验可用能力，模型输出只提出建议。

本次用 10 道题实测。初版提示词只有 1 道通过，另 9 道未通过 JSON 或字段校验。明确英文标签并加入两个示例后，同一组题复测为 10/10。这组题用于调试提示词，下一轮要另加新题，才能检验它能否处理没见过的问法。

## Day 5｜让程序执行一次模型提出的工具请求

工具调用实验把 `add` 的名称、用途和参数结构交给模型。模型提出调用及参数，应用再检查工具名、解析参数，并通过注册表执行。用“请调用 add 计算 12 加 30”可以清楚观察这条链路。本次模型发出了参数 a=12、b=30 的工具请求，应用执行后返回 42。

这次练习刻意选用可预测、容易核对的工具。把计算改成查生产记录后，仍然需要同样的边界：工具范围、输入校验、用户权限、超时与返回值检查。对于超时、连接失败和无效 JSON，可以分别用不同的错误分类呈现。重试要有上限，尤其是已经向用户发送了部分内容的流式请求。

## Day 7｜用一份文档走通最小 RAG

RAG 在回答前检索相关资料，并把命中的片段放进模型上下文。本周用项目已有的文档解析和切分函数，加载一份文档。召回采用简单的字符词组匹配，输出命中的文件名和片段编号，然后调用真实模型生成带引用的回答。

观察两个地方。先看**召回的片段是否回答了问题**，再看**模型是否正确使用了片段**。如果引用指向不相干的段落，应优先检查切分与召回。下一周接入向量模型后，可以用同一批题目比较两种召回方式。

## 动手复现

在项目根目录运行以下命令。默认使用本地 `http://127.0.0.1:11434/v1` 和 `qwen3:8b`，也可通过 `--url`、`--model` 指定其他兼容服务。

```bash
.venv/bin/python -m examples.week01 chat
.venv/bin/python -m examples.week01 routes
.venv/bin/python -m examples.week01 tool
.venv/bin/python -m examples.week01 rag --document docs/module-interactions.md --question '模块如何交互？'
```

可以把 chat 命令的地址换成 `--url http://127.0.0.1:1/v1`，观察模型服务不可用时命令如何返回错误并退出。

运行后记录每道题的**预期路由、实际路由、引用片段和失败类型**。挑一条失败样例，只改一个因素，再用原题复测。这份记录会成为下周比较真实向量检索效果的基线。
