# 01 · 从 LLM 到 AI Agent（二）：什么是LLM

**AI芯世界 · 大模型学习实战**

> 问 AI「设备报警后怎么复位」，它可能给出一段条理清楚的操作步骤。可如果你没告诉它设备型号，也没给它操作手册，这些步骤从哪里来？理解 LLM 怎样生成答案，就能判断哪些回答可以参考，哪些必须查证。

## 一、什么是 LLM？

LLM 是 **Large Language Model**，即**大语言模型**。它从大量训练数据中学习语言结构、概念关联和任务模式，训练成果保存在模型参数中。输入一段文字后，模型可以生成回答，也可以完成摘要、翻译、分类、代码编写等任务。

这里有三个容易混淆的词：

| 名称 | 可以怎样理解 |
|---|---|
| **模型** | 接收输入并产生输出的计算系统，例如我们在项目里调用的 `qwen3:8b` |
| **聊天应用** | 用户使用的界面和服务，负责会话历史、文件上传、模型调用等 |
| **AI Agent** | 围绕任务选择动作、调用工具、读取结果并继续执行的应用系统，LLM 可以参与其中的判断与生成 |

同一个模型可以接到聊天界面，也可以用在后台，把用户的问题分类为「查文档」「查数据」或「需要澄清」。

## 二、语言模型是怎么发展到今天的？

这条时间线选取了几个节点，帮助我们理解今天的对话模型从何而来。

- **Transformer 之前**，统计语言模型可以用词序列的出现频率估计接下来可能出现什么。后来的循环神经网络用内部状态处理序列，让模型有能力利用更长的上下文。
- **2017 年，Transformer 提出。** 它用注意力机制处理序列中的位置关系，减少了训练时对逐步递归计算的依赖，为后续大规模训练提供了架构基础。 [Transformer 原论文](https://arxiv.org/abs/1706.03762)
- **2018 年，BERT 展示了预训练的价值。** 先从大量文本学习表示，再针对下游任务微调。它的训练会利用被遮住位置的左右上下文，适合说明语言模型也可以服务于理解类任务。 [BERT 原论文](https://arxiv.org/abs/1810.04805)
- **2020 年，GPT-3 展示了少样本能力。** 把任务说明和几个例子直接放进输入，模型就能尝试按示例完成新输入。这个过程发生在推理时，无需为每次提问更新参数。 [GPT-3 原论文](https://arxiv.org/abs/2005.14165)
- **2022 年，InstructGPT 展示了指令跟随训练。** 研究人员利用人工示范与偏好反馈，让模型更符合用户对答案的期待。论文也记录了模型仍会犯简单错误。 [InstructGPT 原论文](https://arxiv.org/abs/2203.02155)

## 三、LLM 怎样生成一段回答？

以常见的 GPT 类生成模型为例，可以把过程拆成**训练**和**推理**两个阶段。 [GPT-3 原论文](https://arxiv.org/abs/2005.14165)

### 训练时，模型学习怎样续写

训练文本先被切成 **Token**。一个 Token 可能是字、词的一部分或标点，具体取决于分词器。模型读到前面一段 Token 后，会给下一个 Token 的各种候选项分配概率。训练程序用真实的下一个 Token 计算误差，再调整参数。大量重复后，模型逐渐学到语法、概念关联以及代码等文本的结构。

预训练完成后，模型还可以接受指令微调或偏好训练，学习怎样回应任务、遵循格式、处理不清楚的请求。 [InstructGPT 原论文](https://arxiv.org/abs/2203.02155)

### 推理时，模型根据当前输入逐步生成

1. **切分输入。** 系统提示词、对话历史和当前问题都转换成 Token，进入当前上下文。
2. **计算上下文。** 注意力机制让模型在处理当前位置时，对前文的不同位置分配不同权重。比如「它」可能需要结合前文提到的设备才能理解。 [Transformer 原论文](https://arxiv.org/abs/1706.03762)
3. **选择下一个 Token。** 模型计算概率，解码策略选出一个候选，把它加入已生成内容，然后继续计算。聊天界面逐段出现的文字，可以通过流式接口传输。

我们在本地练习中让 `qwen3:8b` 记住编号 `AI-07`，下一次请求把前一轮消息也传给模型，它成功答出了编号。这个实验展示的是**应用把历史带进了当前上下文**。如果要支持跨会话记忆，应用还需要存储和读取机制。

## 四、LLM 有哪些缺点？

| 局限 | 会遇到什么 | 应用怎么处理 |
|---|---|---|
| **可能编造事实** | 设备型号不明，模型仍可能生成看似合理的复位步骤 | 要求回答引用有效手册。证据不足时请求补充型号 |
| **缺少实时或私有数据** | 用户问「昨天一线产量」，模型只有问题文本可供参考 | 由系统通过授权的只读工具获取数据，并标注日期和统计口径 |
| **上下文有限** | 历史消息和文档过长，关键内容可能被截断或遗漏 | 保留相关历史，只检索需要的文档片段，并用题集验证 |
| **输出会波动** | 同类问题有时返回正确标签，有时字段缺失或选错分类 | 做结构校验、错误处理和回归评测，分别统计格式与业务错误 |
| **运行有成本** | 长文档、多轮调用和并发请求会占用算力，增加响应时间 | 测量首字延迟、总耗时和 Token 用量，再调整上下文与调用次数 |

模型的回答越流畅，读者越容易把它当作已经核实的结论。在操作规程这类场景里，**设备型号、文件版本和引用位置**比回答语气更值得检查。指令微调可以改善输出行为，事实错误依然需要通过证据和评测发现。 [InstructGPT 原论文](https://arxiv.org/abs/2203.02155)

## 五、从 LLM 到 Agent，中间还要接什么？

把工厂里的三个问题放在一起，区别就很直观了。

- **「把这段交接班记录总结成三条。」** 用户已提供完整记录，LLM 可以直接完成文本整理。
- **「这台设备报警后怎么复位？」** 系统先在获授权的资料中找到对应型号和版本的手册，再让模型根据片段回答并附来源。这种做法叫 **RAG（检索增强生成）**。 [RAG 原论文](https://arxiv.org/abs/2005.11401)
- **「查昨天哪些设备停机，再按手册整理核查项。」** 应用先调用授权工具查记录，再根据返回的设备型号检索手册，最后组织结果。流程可以预先编排。需要根据中间结果选择下一步动作时，可以用受限的 Agent 执行循环，并为它设置权限、超时和停止条件。

可以做一个五分钟实验。先只给模型一道设备操作题，再给它一段带页码的相关手册，要求逐条标注依据。比较两次答案里**哪些句子能在资料中找到证据**。这个观察会直接用到下一篇的主题：怎样把问题、背景和输出要求写成一条可验证的 Prompt。
